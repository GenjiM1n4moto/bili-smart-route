# Bilibili Smart Route · B站智能选路

[简体中文](README.md) | [English](README.en.md) | **日本語**

**海外から Bilibili を見るときの、マイナー動画や高ビットレート 4K の再生停止を解消します。** Tampermonkey / Violentmonkey 用のユーザースクリプトです。動画ファイルごとに CDN のキャッシュ状況を実測し、キャッシュがあれば Bilibili が割り当てた海外ノードをそのまま使い、なければ中国本土のミラーに切り替えます。さらに複数ミラーからの並列取得と先読みで、国際回線の帯域を使い切ります。

## 対象ユーザー

中国本土の外から Bilibili を見ていて、人気動画は問題ないのに**マイナー動画・古い動画・4K がよく止まる**人向けです。開発者本人は**日本**で開発・テストしています。他の地域では割り当てられるノードが異なり、効果も変わる可能性があるので、フィードバックを歓迎します。中国本土のネットワークではテストしておらず、通常は不要です。

## マイナー動画が止まる理由

Bilibili は海外のユーザーに海外 CDN ノード（例：`upos-sz-mirrorcosov`、Akamai）を割り当てます：

| ノードの状態 | 実測速度 |
|---|---|
| 海外ノードに**キャッシュあり**（人気動画、最近視聴された部分） | 100–280 Mbps、最初のバイトまで 30–80 ms |
| 海外ノードに**キャッシュなし**（マイナー動画、未視聴の部分） | 0.7–6 Mbps、国境を越えてオリジンから取得 |
| 中国本土ミラー（hw / ali / cos …、オリジン側で必ずファイルあり） | 1 接続あたり 10–75 Mbps、最初のバイトまで 0.1–2 秒、時間帯による変動大 |

4K には 7–30 Mbps が必要です。そのため、マイナー動画が海外ノードに当たると必ず止まります。一方、人気動画を無理に本土ミラーへ切り替えると、かえって遅くなります。

よくある高速化スクリプトは、ファイルの**先頭**だけを測る（先頭はほぼ必ずキャッシュされているので「速い」と誤判定する）か、すべての動画を一つのノードに強制的に切り替える（もともと速かった動画まで遅くなる）かのどちらかです。

## 仕組み

1. **ファイルごとに判定し、先頭ではなく範囲内の数か所を測る。** プレーヤーがファイルの大きなセグメントを取得する前に、Bilibili が割り当てたネイティブノードでその範囲の**中ほどと末尾**を測り（数 MB 以上のセグメントでは 3 か所）、すべてにキャッシュがあるときだけ「キャッシュあり」と判定します。測定値はブラウザのネットワーク層のタイミングで補正するので、ページが重くてもキャッシュのあるノードを「なし」と誤判定しません（逆も同様）。キャッシュがあればネイティブノードに直結し（複数のノードにキャッシュがある場合は Bilibili が最初に指定したノードを優先）、人気動画には一切影響しません。
2. **先読み探査。** ネイティブノードを使っている間は、再生位置の約 15 秒先を探り続け、キャッシュのない区間を見つけたら止まる前に切り替えます。以降のセグメントは使用中のノードだけを再確認し、そのノードにキャッシュがなくなったときだけ全ノードで測り直します。あるノードへのリクエストが数秒たってもデータを受信できない、または今の速度ではプレーヤーのタイムアウトに間に合わない場合は、早めに打ち切り、プレーヤーにすぐ別のノードで再試行させます。
3. **キャッシュがなければ本土ミラーへ。** 候補は Bilibili 公式の UPOS ミラー（署名付き URL をそのまま使える）で、実測の実効スループット（最初のバイトまでの遅延込み、時間とともに減衰）で順位を付け、切り替える前に小さなリクエストで使えることを確認します。
4. **複数ミラーの並列取得 + 先読み。** 本土ルートでは動画ファイルを 2 MB のブロックに分けて最大 3 つのミラーから同時に取得し、約 20 秒（最大 64 MB）先まで先読みします。プレーヤーの要求にはメモリから直接応答します。3 秒進まないブロックは別のミラーから取り直します。切り替える前に各ミラーへの接続を温めて確認し、プレーヤーが待っているブロックが遅れたときは、すでに実績のあるミラーで接続を 1 本追加して補います。
5. **自動保護。** プレーヤーがエラーを出すか、1 分以内に並列取得が 3 回失敗すると、そのページでは通常のリクエストに戻ります。
6. **ブラウザキャッシュの落とし穴を回避。** Akamai ノードはセグメントの応答に 1 年のキャッシュ期間を付けて返します。ブラウザがそれをキャッシュすると、同じファイルへの範囲リクエストが 1 回おきにファイル全体（数百 MB）で返ってきて、セグメントが必ずタイムアウトし、長い動画を倍速で見るとほぼ止まりっぱなしになります。スクリプトは Akamai へのリクエストに範囲ごとのパラメータを付けます。CDN 側のキャッシュには影響しません。ほかのノードで同じことが起きたら、そのリクエストをすぐに終わらせてプレーヤーに再試行させ、以降はそのノードにもパラメータを付けます。

## テスト環境

- **地域**：日本、家庭用ブロードバンド。開発とテストはすべて開発者本人が日本で行いました。
- **ブラウザ**：Chrome + Tampermonkey 5.5、大会員（プレミアム会員）アカウントでログイン（4K 再生可）。
- **Bilibili が割り当てたネイティブノード**：日本の IP には `upos-sz-mirrorcosov`（Tencent Cloud 海外）+ `upos-hz-mirrorakam`（Akamai）が割り当てられ、テスト中に PCDN / P2P ノードは見られませんでした。
- **中国本土ミラー**：1 接続あたり 10–75 Mbps、最初のバイトまで 0.1–2 秒。テストは中国時間の深夜（約 23:00–02:00）に行いました。同じミラーが 1 時間以内に 60–75 Mbps から 10–30 Mbps まで落ちるなど、国際回線の変動は大きいです。

他の地域（北米、欧州、東南アジア、香港・マカオ・台湾）では、割り当てられるネイティブノードや国際回線が異なる可能性があります。他の地域でお使いの方は、Issues にパネルのスクリーンショットを送っていただけると、デフォルト値の調整に役立ちます。

## 実測結果

上記の日本の環境で（当時の本土ミラーは 1 接続あたり約 10–30 Mbps）：

| 動画 | スクリプトなし / 単一ノードへの切り替えのみ | 本スクリプト |
|---|---|---|
| マイナーな 4K AV1（7.7 Mbps） | ネイティブノードは 0–6 Mbps、再生開始直後から停止 | 本土に切り替え、約 40 Mbps、50 秒以上先までバッファ |
| マイナーな 4K AVC（29.7 Mbps） | 単一の本土ミラーではぎりぎりで、バッファが 19 秒から 3 秒まで減少 | 複数ミラー並列：**停止 0 回、1822 フレーム中ドロップ 0、常に 30 秒以上先までバッファ** |
| マイナーな 4K AVC（30 Mbps）、途中から再生 | 45 秒以内に再生が始まらない | 約 10 秒で連続再生に入り、その後は停止 0 回、常に 30 秒以上先までバッファ |
| 人気動画 | 通常は快適だが、ノードが混んでいると遅い（ある測定では再生開始まで 38 秒） | キャッシュがあればネイティブノードに直結し、遅い区間では本土に切り替え（同じ測定で 2 秒で再生開始、停止 0 回） |

## インストール

1. [Tampermonkey](https://www.tampermonkey.net/) または [Violentmonkey](https://violentmonkey.github.io/) をインストールします。
2. **Chrome / Edge 138 以降は必須：** `chrome://extensions`（Edge は `edge://extensions`）を開き、Tampermonkey の「詳細」→ **「ユーザー スクリプトを許可する」（Allow User Scripts）** をオンにします。このスイッチがオフだと、ユーザースクリプトは一切動きません（Tampermonkey のアイコンにも警告が出ます）。
3. **[最新版をインストール](https://github.com/GenjiM1n4moto/bili-smart-route/releases/latest/download/bili-smart-route.user.js)** をクリックすると、スクリプトマネージャーのインストール画面が開きます。この方法で入れると [Releases](https://github.com/GenjiM1n4moto/bili-smart-route/releases) に合わせて自動更新されます。マネージャーで新規スクリプトを作ってファイルの内容を貼り付けることもできますが、その場合は自動更新されません。
4. Bilibili Accelerator（realzza）など、同じく動画リクエストを書き換えるスクリプトを使っている場合は、どちらか一つだけを有効にしてください。

## 使い方

動画を開くと、左下に半透明の **⚡** ラベルが表示されます。ラベルとパネルは中国語・英語・日本語に対応しており、既定ではブラウザの言語に合わせて表示されます。パネル右上の「中 / EN / 日」で切り替えることもでき、選んだ言語は保存されます：

- 🟢 **ネイティブ**：海外ノードにキャッシュがあり、直結。
- 🟠 **本土**：本土ミラーに切り替え済み。複数のミラーを使っているときは `hw+ali` のように表示。

クリックするとパネルが開きます。現在のファイルのルートと速度、この動画の停止回数と最初のフレームまでの時間、各本土ミラーの実測スループット、切り替え履歴と、「スクリプトを一時停止」「複数ミラー並列：オン/オフ」「ミラー統計をリセット」「ログを書き出す」の 4 つのボタンがあります。全画面表示中はラベルが自動で隠れます。

**4K のヒント：** プレーヤーの設定で動画コーデックの優先を AV1 または HEVC にしてください。同じ 4K 動画でも、AVC では 17–30 Mbps 必要ですが、AV1/HEVC なら 6–13 Mbps で済みます。

## よくある質問

**左下に ⚡ ラベルが出ない？** 順に確認してください：

1. **「ユーザー スクリプトを許可する」はオン？** Chrome / Edge 138 以降では、拡張機能の詳細ページで「ユーザー スクリプトを許可する」（Allow User Scripts）がオフだと、スクリプトは一切動きません。インストールの手順 2 を参照してください。
2. **スクリプトは有効？** Bilibili の動画ページでツールバーの Tampermonkey アイコンをクリックし、メニューに「Bilibili Smart Route」（中国語のブラウザでは「B站智能选路」）があって、スイッチがオン（緑）になっているか確認してください。
3. **サイトは正しい？** スクリプトは `bilibili.com` でのみ動作します。国際版の `bilibili.tv` には対応していません。
4. **それでも分からない？** 動画ページで F12 を押してコンソールを開き、`window.__BAX__ && __BAX__.version` と入力します：
   - バージョン番号が表示される：スクリプトは動いています。ラベルが薄いだけなので、左下にマウスを載せるとはっきり見えます。
   - `undefined` と表示される：スクリプトが動いていません。手順 1・2 に戻ってください。

## 設定

**設定は不要です。** 以下はデフォルト値で、インストールした時点でこの値で動きます。変えたい項目だけを書けば十分です（例：`JSON.stringify({ readAheadMaxMB: 128 })`）。設定は Bilibili サイトのブラウザストレージに保存され、スクリプトを再インストール・更新しても消えません。

`www.bilibili.com` のコンソールで実行してから、ページを再読み込みしてください：

```js
localStorage.setItem('bax.cfg.v1', JSON.stringify({
  multi: true,          // 本土ルートで複数ミラー並列 + 先読み
  multiHosts: 3,        // 同時に使う本土ミラーの数
  readAheadSec: 20,     // 何秒先まで先読みするか
  readAheadMaxMB: 64,   // 先読みの上限（MB）
  storeCapMB: 192,      // タブごとの動画ブロック用メモリ上限（MB）
  keepBehindMB: 16,     // 再生済みの部分をどれだけ残すか（MB）
  hotMinMbps: 12,       // ネイティブノードの測定値がこれを超え（かつ現在のビットレートに十分なら）「キャッシュあり」と判定
  ui: true,             // 左下のラベルを表示するか
  lang: 'auto'          // パネルの言語：auto（ブラウザに合わせる）| zh | en | ja
}));
```

`{"enabled": false}` でスクリプトを完全に無効化できます（パネルからもワンクリックで一時停止できます）。

## 通信量とリソース

- 大きなファイルの再生開始時に約 0.5–1.5 MB の追加測定を行い、最大 3 つの本土ミラーにそれぞれ 64 KB の準備リクエストを送ります。ネイティブノード使用中は、探査範囲の約半分進むごとに 256 KB を追加で探査します。
- 本土ルートでは最大 64 MB 先まで先読みし、最大 3 つのミラーにそれぞれ最大 2 本のリクエストを同時に出します。
- 本土ルートでは、1 タブあたり通常約 30–100 MB のメモリを動画ブロックのキャッシュに使います（先読み分と、再生済み部分のうち残しておく 16 MB）。上限は 192 MB です。

## プライバシー

- データの収集・送信は一切行わず、通信先は Bilibili 自身の CDN ドメインだけです。
- ミラーの速度統計はブラウザ内（`localStorage` の `bax.stats.v2`）にだけ保存されます。
- 視聴記録もブラウザ内（`bax.hist.v1`、約 256 KB、古いものから自動削除）にだけ保存されます。動画ごとに 1 件で、BV 番号、画質、最初のフレームまでの時間、停止の回数と時間、ホストごとの通信量、切り替え履歴を記録し、あとから停止の原因を調べるのに使います。パネルの「ログを書き出す」で、ミラー統計と一緒に JSON ファイルとして保存できます。**書き出したファイルには視聴した動画の BV 番号が含まれる**ので、共有する前に確認してください。消去するにはコンソールで `__BAX__.clearHistory()` を実行します。
- 診断コマンド `__BAX__.dump()` が出力するのはホスト名と統計だけで、動画 ID や署名付きの動画 URL は含まれないため、Issue にそのまま貼っても安全です。

## 制限事項と既知の問題

- 主に海外のネットワーク、通常の投稿動画、1080p–4K でテストしています。番剧（アニメ）、講座、他サイトに埋め込まれたプレーヤー、中国本土のネットワークは十分にテストしていません。ライブ配信には一切手を加えません。
- 現行の Web プレーヤーが「メインスレッドの XHR でセグメントを読み込む」方式に依存しているため、Bilibili の仕様変更で動かなくなる可能性があります（その場合は自動保護で通常のリクエストに戻ります）。
- Bilibili はタブが表示されているときにしか動画を読み込まないため、バックグラウンドタブでの停止は本スクリプトとは関係ありません。
- 本土ミラーの一覧はコードに直接書かれているため、ドメインが使えなくなったら更新が必要です。

## 問題の報告

[Issues](https://github.com/GenjiM1n4moto/bili-smart-route/issues) に、動画の BV 番号、画質とコーデック、パネルの「切り替え履歴」のスクリーンショット、またはコンソールで `JSON.stringify(__BAX__.dump())` を実行した出力を添えてください。パネルの「ログを書き出す」で作ったファイルも役立ちます（視聴した動画の BV 番号が入っているので、関係のないものは先に削除してください）。
